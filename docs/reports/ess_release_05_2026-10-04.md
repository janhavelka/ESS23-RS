## Implemented APIs and lifetimes

`ReadTarget` holds application ID, address and binding generation. Preparation
snapshots it, the nonzero operation ID, active host tuple, optional four wiring
declarations and one immutable absolute deadline. `PreparedRead` owns eight
request bytes. `nextRead` is a const yield; repeating the yield performs no I/O.
The application prevents repeated admission with one current owner request ID.
`advanceRead` copies each raw reply/prefix (maximum37 bytes), received length,
qualified closure bounds, codec status, accepted TX count, uncertainty and
application-defined transport detail. It retains no frame pointer.

Rejected correlation/envelope/time arguments leave the context unchanged. OK
from advanceRead means consumed event; the operation can still be FAILED.
Checked device exceptions retain EXCEPTION/detail separately from malformed
frames and transport errors. Only complete successful operations publish a new
typed observation; failed/partial getters preserve the previous output.

The core performs no transport, logging, allocation, task work, clock reads,
retry or settings change. All handwritten types are outside generated Types.h.
The application maps owner FRAME/evidence to portable events; numeric transport
details are the retained Runner reason, or -1 for an impossible integration
envelope. That envelope is terminalized without replay or decoded publication.

Eight frontend operation slots reserve retention across configuration windows.
After copying an intermediate result, the application explicitly releases its
owner result before admitting the next window. Other eligible work may run
between windows. The final context and final owner result, when present, remain
until explicit frontend release. A local cancellation between steps needs no TX;
active cancellation waits for physical settlement. Qualified final completion
can win cancellation; a completed intermediate frame cannot resume a cancelled
operation. Recovery invalidates the application binding generation immediately
and preserves old outcomes while preventing continuation. An RTU response has
no wire request ID; bit-identical delayed traffic remains an explicit limitation.

Commands are `read identity [address]`, `read config [address]`,
`profile ess_rs identity [address]`, `profile ess_rs config [address]`, `caps`
and `profile ess_rs caps`. Accepted/terminal names are canonical `read-identity`
and `read-config`; command IDs and operation IDs are independent. Nine asynchronous
correlations cover eight frontend requests plus the separate recovery outcome.
Result inspection is non-consuming. Local config reports cache IDs/targets/
binding generations separately from active host settings; caches survive failure
and result release. Probe health remains its separately labelled cached probe.

Input96 bytes/six tokens,32 input characters and64 USB bytes per loop remain
bounded. Console output grows from1536 to4096 bytes for actual five-window
provenance; its tested full-width record3382 is tested with unknown raw values,
maximum IDs/tuple values and20-digit timestamps. No second command engine or
request queue was added.
