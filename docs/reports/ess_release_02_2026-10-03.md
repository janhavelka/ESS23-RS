## Implementation and ownership handoff

Application headers remain under `examples/common/`; no installed core API,
Arduino/IDF type, RTOS ingress, heap, clock, retries, other driver or ASCII
framing was added. One cooperative context exclusively owns every BusOwner
method, Runner and port. Logical producers use local indices and small adapters
in that context. One pending ring holds both classes; no duplicate producer
queues or independent active-ownership flags were added.

`BusStorage` now also requires caller-owned producer slots (1..65535), and
configures reserved urgent portions of the existing pending/result capacities.
Original copied request bytes, immutable expectations, stable request IDs,
non-consuming result access and synchronous checked-parser settlement remain.
The completion adds producer/sequence, eligibility/dispatch deadline, urgency
and first cancellation cause. Response success remains checked data/acknowledgement,
never proof of motion completion. Target/configuration fields are application
metadata, not an axis reservation.

`recover` replaces the old empty-queue boolean owner API with a bounded operation:
reserve a distinct control result, terminally cancel old queued work, invalidate
all continuations, settle physical TX, discard stale RX, observe quiet, then
attempt recovery. `recoveryResult`/`releaseRecovery` preserve its own outcome
under full ordinary/urgent pressure. Recovery IDs are local to the live owner;
command correlation remains prompt 03. Failed recovery leaves admission-to-
dispatch interlocked; releasing its result cannot clear the fault.

Each ordinary producer preserves FIFO, including deferred heads. Cyclic dispatch
offers turn fairness among eligible ordinary heads; urgent FIFO may bypass that
class. No ordinary fairness is promised under an unbounded urgent flood.
Configuration changes require `invalidateProducer` before publishing the changed
configuration; sequence cancellation invalidates the token, including waits
with no queued step. Same-axis operation reservation remains later work.

For 03: use these actual APIs and the [owner contract](../bus_owner.md); remove
direct console Runner admission there. Apply recovery cancellation through the
CLI, preserve interrupted and control results independently, classify every
FRAME with its admitted validator, distinguish command IDs from request/sequence/
recovery IDs, and measure the actual finite queue/result/service limits. A sticky
adapter error is reported as recovery `READ_ERROR`; explicit adapter cleanup must
occur only after physical TX/DE settlement before a fresh recovery attempt.

## Independent review and fixes

The scheduling/liveness reviewer inspected actual source, storage boundaries,
callers, diff and FieldCore recovery read-only. The cancellation/uncertainty
reviewer authored independent fake tests in `test/bus_scheduling_test.cpp` and
audited integrated source. Both re-reviewed the corrections; the lead checked
the actual code and test assertions independently.

Confirmed and fixed before delivery:

- Group cancellation repeatedly shifted the ring; one linear compaction now
  preserves FIFO and repairs owned byte pointers.
- Repeated cancellation could advance a sequence generation again or replace its
  first cause. It now invalidates once and retains the original cause/cutoff.
- Queued cancellation after a deadline could mask expiry; absolute/dispatch
  expiry now wins and retains the original deadline with zero accepted TX.
- Cancellation after physically completed history but before the absolute deadline
  could publish cancellation when 64 reads were insufficient. A separate immutable
  RECEIVE cancellation cutoff preserves qualified earlier completion across passes,
  rejects later closure and reports straddling evidence as uncertain.
- Recovery expiry while a previous cancellation was settling could lose fault
  visibility. The retained interrupted request ID keeps it visible independently
  of first cancellation cause.
- Historical success arriving after recovery expiry could reopen dispatch. Collection
  preserves the success but explicitly retains the recovery interlock, even if the
  failed control result was already released.
- A poll finishing the active frame and a recovery drain could consume two read
  budgets in one service. Draining now waits for the next service; the regression
  observes 26 reads followed by 64 on separate calls.
- Failed sequence creation at generation exhaustion could mutate producer state;
  it now rejects before advancing and leaves output/state unchanged.

No confirmed source defect remained in either final independent audit. The latency
bound is conditional, not a measured physical stop guarantee. Urgent work queued
before explicit recovery is cancelled; fresh urgent admission after recovery is
required. A bit-identical late RTU reply remains fundamentally indistinguishable.
