## Fixes and independent audit

Bare `driver`, `io`, `segment`, `control` and `tuning` groups reuse their
existing checked profile parsers. Redundant family conditions were removed.
Metadata/help/caps now reflect each installed callback, including local-only
home inventory, typed-only health checks and reset-only stats consumers.
The blanket requirement for unrelated probe/snapshot/recovery callbacks was
removed. Profile caps uses the same capability reply as caps. Public core
signatures and generated types are unchanged.

`useaddr` is an idle host selection, with no motor traffic. Changed selection
invalidates dependent scales/origin/configuration/observations, marks wiring
unknown and preserves original retained contexts and physical uncertainty.
Late old-generation probe/identity delivery cannot restore confidence.
`motion-profile forget` explicitly releases only the saved host snapshot.
Monitor query/off remains available during host faults and exclusive ownership;
off cancels its continuation and settles physical transmission.

Input JSON now reports assignment and declared wiring separately from observed
levels. Homing admission distinguishes invalid, unresolved and unimplemented.
Torque/current motion and serial segment start remain unsupported. Settings
access never claims those motion modes. The checker audits every installed
free-function declaration and rejects fictitious producing CLI routes; metadata,
members, codecs and sequencers are accounted without inflating device coverage.

Three parallel reviewers inspected API/CLI inventory, state/effects and
application/Python tests. Each audited the integrated production diff; root
verified concrete findings against code and failure cases. A final independent
review checked the optional-callback help correction. No unresolved defect in
the implemented integration path was reported; named owning-prompt gaps remain.

FieldCore HEAD `60023936c2caf166eaf43f82254c1d9540b8522f` was freshly inspected
read-only, including its RS485 task, queues/results, backend and CLI. Cooperative
ownership and request/result vocabulary are reused. Deliberate differences are
motor-write uncertainty, explicit non-consuming result retention/release,
checked FC06 echoes, longer frames and absence of sensor retry/framework ingress.
No FieldCore source was changed.

## Reproduced hardware discrepancy and correction

The preceding-image campaign moved100 native increments from raw198 to298.
The following absolute return was refused by the Python fixture guard before
move TX. A deliberate second run reproduced the refusal at raw298 with15
read frames and no motor writes. The absolute refusal was expected outside
the recorded0..250 envelope. Follow-up inspection also found that the harness
applied that window to unrelated relative/stop phases, unnecessarily rejecting
otherwise eligible bounded relative tests.

The correction confines that guard to absolute/return experiments. Bounded
relative100 and stop-test250 commands retain the firmware's checked native
target/speed/ramp envelope and do not require a host origin or physical feedback
mapping. Tests prove raw298 and unknown/signed-looking feedback are accepted
only for relative phases, while absolute/return remain refused. The corrected
campaign deliberately began at298, completed the relative move, observed
RUNNING before a normal stop during a finite250 move, then verified stopped
state and session parameter restoration. It did not retry the failed absolute
command or alter firmware limits. Failed and passing raw logs are archived.

Moving-stop application interval was117327us from reported start through new
stopped observation. This is software/drive-report evidence, not independent
shaft deceleration or electrical latency. Acknowledged trigger/stop and fresh
running/stopped evidence remain distinct; the interrupted move retains its
cancelled/interrupted-by-stop result.
