# MotorControl-RS 1.0.0

First release tag: `v1.0.0`. Earlier 0.x numbers were development snapshots,
not published releases. [CHANGELOG](../../CHANGELOG.md) combines that history.
The tag identifies the release source; GitHub release publication is a separate
user action. No motor firmware update is included.

## What is included

- C++11 core: exact units/targets, checked ESS-RS codecs, typed observations,
  settings and caller-owned operation sequences.
- Shared ESP32-S3 application for Arduino and native ESP-IDF: console, one bus
  owner, priority stop, retained outcomes and bounded diagnostics.
- Simple position controls plus detailed native/profile commands.
- Finite Python scenarios, repeatable software verification and clean packages.

[Getting started](../getting_started.md) explains normal use.
[API/CLI coverage](../ess_api_cli_coverage.md) is the implementation inventory;
[console help](../console.md) describes commands and result handling.

## Supported hardware and operating envelope

| Item | Scope |
| --- | --- |
| Bench motor | ESS23-RS20; raw model `0x4EEA`, firmware word `0x0029` |
| Connection | Address 1, 115200 8N1; power and RS485 only; secured free shaft |
| Arduino | ESP32-S3, Arduino 3.3.11 / IDF 5.5.5; latest position-boundary HIL |
| Native ESP-IDF | ESP32-S3, IDF 5.5.5; earlier finite motion/stop/load evidence; latest policy build-tested |
| ESP32-S2 | Core and portable application compile checks only; no S2 UART adapter or hardware qualification |
| Other motors | ESS23-RS10 documented but not bench-qualified; other profiles unimplemented |

Default typed finite-position policy requires active subdivision and combines
2,000 rpm, 200,000 increments/s and native ramps 100..2,000 ms. At 51,200
subdivision the ceiling is 234 rpm. No silent clamping occurs. Raw codecs do
not enforce operation readiness or this policy. See [position API](../ess_position.md).

The [four-hour campaign](../reports/2026-10-07_rate_boundary.md) completed 4,580
cases within the narrower tested envelope. The
[boundary follow-up](../reports/2026-10-07_position_limits.md) completed 408
motion/stop cases and 68 no-TX overspeed rejections across 17 subdivisions.
Its 21,553 checked frames had no transport failure or new drive alarm.
These are finite, drive-reported results, not absolute reliability or calibrated
shaft/thermal/electrical measurements. Original failed attempts remain retained.

## Remaining limits

- High-speed persistent RUNNING and reset-like loss of volatile settings remain
  unresolved outside the conservative envelope. A 200 kHz input specification
  does not establish an internal serial-motion formula or the failure cause.
- Firmware word `0x0029` is readable; its vendor release mapping and an applicable
  motor firmware update procedure are unresolved.
- Nine native-family gaps remain: arbitrary profile candidate/archive workflows,
  positioning start-speed setter, standalone velocity/homing parameter reads,
  homing auxiliary choices/remaining methods, nonzero homing offsets, early
  collision-register access and position-interruption options. Eighteen paired
  setters remain guarded: two limits and sixteen stored position targets.
- Velocity, homing, negative encoding, external switches/loads, persistence after
  restart and physical acceleration/position accuracy have separate unqualified
  cases. Software paths are not evidence that every case ran on hardware.
- No live speed-update API, serial segment start, torque/current motion,
  communication-loss stop or industrial certification is claimed.
- A confirmed stop clears current motor ownership; retained uncertain outcomes
  remain evidence and must never be automatically replayed.
- The replacement shared USB driver has finite regression evidence, including
  the later boundary run. A fresh overnight run on that driver remains open.

The [backlog](../backlog.md) and [roadmap](../roadmap.md) retain the detailed
open work. Historical reports keep their original version, image and outcome.

## Reproduce and package

Use a fresh checkout of `v1.0.0`, then follow [verification](../verification.md).
The release preparation uses the same quick/full verifier and four hosted CI
jobs: GCC, Clang, Arduino and native ESP-IDF. Hardware is not part of hosted CI.

```sh
git checkout v1.0.0
python -m pip install -r scripts/requirements-verification.txt
python scripts/verify.py --mode full --build-dir build/release-1.0.0
```

Full mode needs the pinned SDKs. `--firmware arduino` or `--firmware idf` selects
a bounded full-build subset; quick mode still runs all native/Python/package
checks. The verifier produces a summary, logs and a core ZIP. It checks generated
files, reference hashes, documentation links, C++11/C++17 public headers,
source/install consumers and absence of catalogue strings in codec-only links.

GitHub source archives contain the full repository. The verifier's core ZIP
contains only library source, headers, CMake/metadata, MIT license, README and
changelog. Vendor references retain separate licensing and are excluded from
that core ZIP. Neither package depends on FieldCore.

## Publish from GitHub

After the annotated tag is pushed and its CI passes, select `v1.0.0` under
**Releases > Draft a new release**. Use **MotorControl-RS 1.0.0** as the title.
Copy the 1.0.0 changelog and link this scope page; do not turn the remaining
qualification gaps into a full-coverage claim. Attach the verified core ZIP
and its checksum manifest if distributing a standalone library archive.

The active repository remains `janhavelka/ESS23-RS`. Canonical package metadata
is prepared for `janhavelka/MotorControl-RS`; the target endpoint is not yet
available. Follow the [rename guide](../repository_rename.md) when renaming.
